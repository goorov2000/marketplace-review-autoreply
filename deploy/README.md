# Перенос на VPS JLP

Рабочая копия — `/srv/jlp/review-autoreply`, пользователь `jlp`, Python 3.12+.
Секреты — `/srv/jlp/secrets/ai-answers.env` с группой `jlp` и правами `0640`.
Секреты не копируются в репозиторий. По умолчанию запуск только показывает ответы.

## Подготовка

Установить обе группы зависимостей в `.venv` рабочего клона:

```bash
uv venv --python /usr/bin/python3 .venv
uv pip sync --python .venv/bin/python deploy/requirements.lock
```

Службы скрывают `/home`, поэтому интерпретатор должен находиться в `/usr/bin`,
а не в пользовательском кэше uv.

В терминале VPS токены маркетплейсов вводятся скрыто; существующий OpenAI-ключ сохраняется:

```bash
/srv/jlp/review-autoreply/.venv/bin/python /srv/jlp/review-autoreply/deploy/configure_marketplace.py wb
/srv/jlp/review-autoreply/.venv/bin/python /srv/jlp/review-autoreply/deploy/configure_marketplace.py ozon
```

Проверка настроек без запросов к API и расходов:

```bash
sudo -u jlp /srv/jlp/review-autoreply/.venv/bin/python /srv/jlp/review-autoreply/deploy/run.py wb --check
sudo -u jlp /srv/jlp/review-autoreply/.venv/bin/python /srv/jlp/review-autoreply/deploy/run.py ozon --check
```

Для предварительного просмотра убрать `--check`: отзывы читаются, ответы генерируются,
но не публикуются. Это вызывает платные запросы OpenAI. На первую проверку задать
`MAX_COUNT=1` в файле секретов; после проверки вернуть рабочий лимит (по умолчанию 20).
Раннер принудительно устанавливает `DRY_RUN=1`, даже если в файле было `DRY_RUN=0`.

## Переключение

1. Остановить старые задания в Render/другом планировщике и дождаться окончания текущего прогона.
2. Проверить кабинет, права токенов и ответы предварительного просмотра каждого маркетплейса.
3. Установить отслеживаемые юниты `jlp-ai-answers-*` через репозиторий JLP и его штатный деплой.
   Не класть их вручную в `/etc/systemd/system`: установщик JLP удаляет неизвестные юниты.
4. Только после проверок создать `/srv/jlp/data/ai-answers/wb.enabled` и/или `ozon.enabled`.
   Без маркера соответствующая служба пропускает запуск, раннер не разрешает `--publish`.

Публикация выполняется только с явным `--publish` и маркером активации. Одна локальная
блокировка на маркетплейс исключает пересечение ручного запуска и таймера. Другой сервер
она не блокирует, поэтому отключение старого расписания обязательно.

Журнал: `journalctl -u jlp-ai-answers-wb.service` (аналогично `ozon`). При ошибке обработки
хотя бы одного отзыва программа возвращает ненулевой код. Общее число попыток за запуск
ограничено `MAX_COUNT`, включая отказы API. Объём чтения Ozon ограничен `MAX_PAGES`;
WB проходит пропускаемые низкие оценки до кандидатов или конца очереди.
Продолжительность каждой службы ограничена десятью минутами в systemd.

Текстовая политика сохранена: WB отвечает на 4–5 звёзд, Ozon использует прежние настройки
пустых отзывов. Ozon просматривает старые необработанные отзывы первыми: если всё окно
`PAGE_LIMIT × MAX_PAGES` состоит из пропускаемых отзывов, до включения надо разобрать
эту очередь или согласовать расширение окна. Сам перенос не помечает такие отзывы обработанными.

Для отката удалить маркер соответствующего маркетплейса, остановить его службу, затем
переключить рабочий клон на проверенный коммит. Старое расписание включать только после
полной остановки VPS-задания. При обновлении кода таймер остановить и дождаться текущего
прогона; не обновлять файлы под работающим процессом.
